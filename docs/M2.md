# Cello M2 Plan

* **Author:** Lucas N. Munhoz
* **Date:** 2026-11-14

## What M2 delivers

Agents work through the `cello` CLI from their own shell, and every change records which agent session made it. The board shows that provenance. When M2 is done, an agent can pick up a CEL task, claim it, comment on it and move it to Done without anyone touching the web app.

## Bootstrap: Cello builds Cello

M2 starts with two tasks that make Cello usable for its own development. After that, every M2 task is claimed and moved through `cello` on Lucas's real board.

## The CLI

One binary, `cello`, compiled with `bun build --compile` and linked into `~/.local/bin`. Every command is a few lines: parse arguments, make one RPC call, format the result. It talks to the server at `127.0.0.1:${CELLO_PORT:-4747}` and starts the server if none is running.

| Command | What it does |
| --- | --- |
| `cello start` | Runs the server on 4747 with `~/.cello` (or `CELLO_DATA_DIR`). |
| `cello whoami` | Prints, as JSON, the identity Cello sees: agent variables, session, project from the working folder. |
| `cello context` | Start here: current project, statuses, labels, tasks this session has claimed, recent activity. |
| `cello task list` | Open tasks in the current project; `--status`, `--label`, `--mine`, `--json`. |
| `cello task get CEL-3` | One task: description, labels, comments, history. |
| `cello task create "Title"` | `--description` or `--body-file -`, `--status`, `--priority`, `--label`, `--parent`. |
| `cello task claim CEL-3` | Assign to this session and move to the first started status. Fails if another live session holds it. |
| `cello task release CEL-3` | Give up a claim without finishing. |
| `cello task move CEL-3 "Todo"` | Move to a status by name. An agent can't move to In Review this way. |
| `cello task submit CEL-3` | Hand finished work to Lucas (CEL-10): `--summary`, `--step` (repeatable), `--attach file` with `--caption`, `--link`. Copies the evidence to the server and moves the task to In Review. |
| `cello task comment CEL-3 "text"` | Or `--body-file -` for markdown from stdin. |
| `cello guide` | The agent conventions (see below). |

**Output:** short text by default (`CEL-3  In Progress  cello CLI: task create, claim, move, comment`), `--json` for scripts. Errors say what to do next, from one table keyed by error tag: "CEL-3 is claimed by Claude Code session 9f2c (active now). Pick another task or run `cello task get CEL-3`."

**Conventions** (`cello guide`, also installed as a Claude Code skill in M2's later steps):

- run `cello context` first
- claim a task before working on it
- comment on progress
- put the task key in commit messages
- when done, `cello task submit` a review packet (summary, steps, videos or screenshots, or test output); it moves the task to In Review, and Lucas approves it or sends it back from the Review page

## Identity and project

- The CLI sends RPC headers from its environment:
  - `x-cello-session`: `CELLO_SESSION`, else `CLAUDE_CODE_SESSION_ID`
  - `x-cello-client`: "Claude Code" when Claude variables are present
  - `x-cello-pid`: `CLAUDE_PID`
  - `x-cello-cwd`: the working folder
  - `x-cello-entrypoint`: `CLAUDE_CODE_ENTRYPOINT`
- `CELLO_SESSION=me` records the human.
- The server's caller middleware turns a session header into an `agent_sessions` row, created on first sight. It hangs off one `actors` row per client ("Claude Code", color from the session id) and is updated on every call (`last_seen_at`).
- **Project from the working folder:** walk up to `git rev-parse --git-common-dir`, then match `project_repos.path`. `--project CEL` overrides it. Unknown folder: the error says to run `cello init` (later in M2) or pass `--project`.
- Every event already stores `actor_id` and `session_id`; from M2 they carry the agent's.

## Claims

New RPCs `task.claim` and `task.release`. They follow the claim rule in SPEC.md, "Settled in review":

- A claim holds until the task is done, released, changed by the human, or the holder is gone.
- "Gone" means the holder's pid is dead (the server checks it, since it runs on the same machine), or 2 hours pass with no call from it when the pid is unknown.
- Taking over writes `task.claim_taken`. The old session's next command warns it.

## Provenance in the web app

- **Card avatar slot:** who created or last changed the task, as an agent icon in the session's color or your initial.
- **Task panel:** "Created by Claude Code · session 2fd0505c · ~/projects/cello", with "Copy resume command" (`claude --resume <id>`). History lines name the agent.
- **Agents section in the sidebar:** sessions active in the last 30 minutes, with their claimed task. Click one to filter the board to its changes.

## Later in M2

- `cello init` registers a repo as a project
- `cello install claude` installs the skill and allowlists `Bash(cello *)`, asking before it edits settings
- `cello hook install`: post-commit hook linking `CEL-n` mentions
- `cello task link`
- `--body-file -` for every long text

## Tests (written first)

1. The CLI's headers resolve to an agent session, created once and reused across calls.
2. `CELLO_SESSION=me` and no agent variables both record the human.
3. The project comes from the working folder, including a worktree of the repo.
4. `task.claim` sets the assignee to the session and moves to the first started status.
5. A second session claiming a live claim fails with a message naming the holder.
6. A claim from a dead pid is taken over and writes `task.claim_taken`.
7. A human change ends a claim.
8. Each CLI command against a real server (integration): context, list, get, create, claim, release, move, comment, with text and `--json` output.
9. The server serves the built web app on its own port, and the origin check allows it.
10. `cello start` refuses to start a second server and prints the running one.
11. Provenance shows on the card and in the panel (e2e, with video).

## Done when

- An agent session finishes a CEL task end to end through `cello` only.
- The board shows which session did each step.
